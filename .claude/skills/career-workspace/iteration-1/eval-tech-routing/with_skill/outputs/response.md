# FE 特化 vs フルスタック -- 技術方向性の壁打ち

## まず結論から

**FE 特化の T 字型が、今のあなたにとって最も合理的な選択。** ただし「FE 特化」の中身を正しく定義することが重要で、「React が書ける」ではなく「FE のアーキテクチャを設計・意思決定できる」まで深めるのが本筋。

---

## 現在地の整理

スキルと経歴を踏まえると、今のポジションはこう。

**FE**: 一人で FE を立ち上げてゼロから設計できるレベル。技術選定、コンポーネント設計、テスト基盤、CI/CD まで一通り自分で判断して回せている。3プロジェクト並行でコンテキストスイッチしながら設計力を磨いてきた実績もある。

**BE**: ORM 経由の DB 操作、C# の API レスポンス修正程度。設計判断を自分でしたことはない。

この差は「ちょっと頑張れば埋まる」ような差ではなく、FE 側に 1 年半分の意思決定の蓄積がある。

---

## なぜ FE 特化が合理的か

### 1. 目標との整合性

テックリードとして目指しているのは「FE チームを率いて設計思想を共有する」こと。この目標に対して BE を広く浅くやっても打点が低い。FE の設計判断を「なぜそうするのか」を言語化してチームに伝えられるレベルまで深めることのほうが、テックリードへの最短距離になる。

### 2. 差別化の現実

エンジニア歴 1 年半で「フルスタックです」と言っても、BE が本職の人には設計力で勝てない。一方で「FE 設計を一人で立ち上げられる + AI 駆動開発の実践知がある」は、経験年数に対して明らかに突出している。尖っているほうが覚えてもらえる。

### 3. 伸ばすべき FE の深さがまだある

自分でも future-goals に書いているが、以下はまだ「これから」の領域:

- **状態管理・データフロー**: Server/Client Component 間のデータ分割戦略
- **テスト設計**: テスト戦略の立案、テスタビリティを意識した設計
- **CS の基礎**: アルゴリズム、ネットワーク、技術選定の「なぜ」を深いレベルで説明する力

これらを先に埋めるほうが、BE に手を広げるより設計力の底上げ効果が大きい。

---

## ただし「FE に閉じる」ではない

FE 特化 ≠ BE を無視する、ではない。

### BE との「接点」は伸ばすべき

future-goals にも「API 設計・データモデリング、BE との接点も含めた設計力を伸ばしたい」とある。これは正しい方向で、テックリードとして BE エンジニアと対等に設計議論するには、以下が必要になる:

- **API 設計の良し悪しを判断できる**: REST / GraphQL のトレードオフ、エラーハンドリング設計、ページネーション戦略
- **データモデリングの基礎**: 正規化、リレーション設計、FE に返すべきデータ構造の提案
- **認証・認可の仕組み**: JWT / セッション / OAuth の理解（FE の実装だけでなく全体のフローを把握する）

これは「フルスタックになる」ではなく「FE エンジニアとして BE との境界を正しく設計できる」ということ。T 字の横棒部分。

---

## 具体的なアクション

今の状況を踏まえて、優先度順に。

### 最優先: FE の深さを埋める

1. **テスト設計を体系的に学ぶ**
   - Testing Trophy（Kent C. Dodds）の考え方を起点に、「何をどのレベルでテストするか」の判断基準を自分の中に持つ
   - 業務の PJ3 が TDD 運用中なので、テスト戦略の振り返りドキュメントを書いてみる（学びの定着 + 発信ネタ）

2. **アーキテクチャの引き出しを増やす**
   - 今の業務は Next.js App Router 中心だが、Remix / Astro / Tanstack Start など異なるアプローチのフレームワークを個人で触って「なぜ Next.js を選ぶのか」を深いレベルで語れるようにする
   - 状態管理は TanStack Query をメインにしているが、Jotai / Zustand / XState など異なるパラダイムの状態管理を理解しておくと設計判断の幅が広がる

3. **CS の基礎を埋める**
   - ネットワーク（HTTP/2, HTTP/3, CDN, DNS）は FE パフォーマンスに直結するので最優先
   - ブラウザレンダリングパイプライン（Critical Rendering Path）の理解

### 次のステップ: BE との接点

4. **API 設計の知識を入れる**
   - 個人プロジェクト（specv の次のバージョンや新しいツール）で自分で API を設計してみる
   - Hono はすでに使っているので、DB 接続（Drizzle + SQLite/Turso あたり）を加えて CRUD を自分で設計する経験を積む

---

## フルスタックが必要になるタイミング

もし将来的に以下のような状況になったら、そのとき改めて BE を本格的に深めればいい:

- 個人プロダクトを一人で作って収益化したい
- CTO / VPoE として技術戦略全体を見る立場になった
- 転職先がフルスタックを求める小規模チーム

今の段階でそこに投資するのは早い。まず FE で「この人に聞けば間違いない」というポジションを作ること。その基盤があれば、BE に広げるのは後からでもできる。

---

## まとめ

| 観点                   | 判断                                                     |
| ---------------------- | -------------------------------------------------------- |
| 短期（半年〜1年）      | FE の深さを埋める（テスト設計、アーキテクチャ、CS 基礎） |
| 中期（1〜2年）         | BE との接点を強化（API 設計、データモデリング）          |
| 長期（必要になったら） | フルスタックへの拡張                                     |

「FE 特化でいくかフルスタック目指すか」は二択ではなく、**今は FE を深める時期で、BE への拡張は FE の基盤が固まってからでも遅くない**、というのが自分の見立て。
