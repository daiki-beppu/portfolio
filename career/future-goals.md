# キャリアビジョン・今後の方向性

## 譲れない核

**学び続ける > 自分の手で作る > AI を活用し続ける**

この3つは不可分で、すべてが揃って初めて自分らしい働き方になる。ただし優先順位をつけるなら、成長が最優先。

---

## 1. テックリードとして目指す姿

### 今と何が違うテックリードになりたいか

現職でも実質テックリードとして技術選定・設計判断を行っているが、一人で判断している状態。次の環境で目指すのは:

- **高い基準の中でのリード**: まず高い技術基準を持つ組織で基準を体で覚える。その上で、基準を引き上げる側に回れるリードを目指す。学びの機会は組織外（コミュニティ・登壇・OSS）でも自分で整備する
- **メンバーがいる中でのリード**: FE チームを率いて、レビューやペアプロを通じて設計思想を共有する経験を積みたい（育成の実績はまだない）
- **より大規模な意思決定**: 受託の個別プロジェクトレベルではなく、プロダクト全体の技術戦略に関わりたい
- **「何を作るか」への関与**: 今は「どう作るか」の判断が中心だが、プロダクトの方向性を技術の視点から提案できる立場を目指す

### リードしたい領域

- **技術選定・設計判断**: フレームワーク選定、アーキテクチャ設計など技術的な意思決定をリード
- **開発プロセス改善**: CI/CD、TDD、AI 駆動開発などの開発フロー全体の設計と改善
- **メンバー育成**: 仕組みで底上げ（テンプレート・ルール・スキル）、レビューを通じた設計思想の共有、ペアプロ / 1on1、ドキュメント・ナレッジ共有

### CTO / VPoE について

将来的にはプロダクトの技術戦略を描くポジションも視野に入れている。今の会社であれば実現可能性が高いが、肩書きよりも成長環境を優先したい。調整業務が増えることは理解しており、必要ならやる覚悟はある。ただし現時点では理想論に近く、まずはテックリードとしての実績を積むことが先。

## 2. AI 駆動開発の未来像

### 現在地と次のステップ

現在は Claude Code のカスタムスキル整備、CLAUDE.md によるルール定義、TDD との組み合わせで「仕様駆動の AI 開発」を実践中。ただし仕様駆動は受託開発（仕様が確定して降りてくる）との親和性が高いからこそ機能している側面がある。

次に目指すのは:

- **AI 向けの設計パターン確立**: AI が扱いやすいコードベース・ルール・スキルの体系化。「テストがちゃんとあればタスク単位なら AI が自律的に回せる」という現状の知見をさらに発展させる
- **チーム全員が AI を使える状態**: 自分だけでなく、チーム全体の AI リテラシーを底上げし、AI 駆動開発を当たり前にする
- **AI エージェントの自律運用**: 直近はタスク単位〜機能単位の自律（issue → 設計・実装・テスト・PR）。将来的には仕様を渡すと機能全体を実装・テスト・デプロイまで行うレベルを目指す

### 自社プロダクトでの AI 駆動開発

自社プロダクトでは仕様が確定していない状態が多いため、仕様駆動ではなく仮説検証型に変わると考えている。AI で素早くプロトタイプを作り、検証して方向を決めるサイクル。テストの重要性はむしろ増す — 仕様が変わりやすいからこそ、テストで守る必要がある。

### AI 時代のコード品質 — キャリアの軸として育てたい領域

AI 駆動開発において、コード品質の担保は最も重要な課題の一つと考えている。テストが正しく書かれていれば AI はタスク単位で自律的に動ける。逆にテストがなければ AI の出力を信頼できない。

**「AI 時代のコード品質」** を大きな旗として掲げ、以下の柱で軸を育てたい:

```
旗: AI 時代のコード品質エンジニア
├── 柱1: AI × テスト（品質の担保）
├── 柱2: AI × リファクタリング（品質の改善）
└── 基礎: DDD / クリーンアーキテクチャ（品質の設計）
```

**なぜこの軸か:**

- **市場の希少性**: AI 駆動開発の実践知とコード品質の両方を語れるエンジニアがほぼいない
- **自分の経験との接続**: TDD × AI 駆動開発のワークフロー確立、Linter/Formatter の段階的進化（ESLint → Biome → ultracite）、100件超のフィードバック対応による品質安定化、PR テンプレートの整備、knip による不要コード検出 — すべて「コード品質を仕組みで担保する」活動
- **FE との相性**: FE のテスト戦略やリファクタリング手法は未成熟な領域が多く、開拓の余地がある
- **リファクタリングへの興味**: コードを改善するプロセス自体にやりがいを感じている

**現状の課題と戦略:**

テストの知見はまだ浅く、古典的アーキテクチャの理解も基礎レベル。まず高い技術基準の組織でテスト文化と設計基準を体で覚え、並行して AI × コード品質の実験を個人で続ける。DDD やクリーンアーキテクチャは「軸」ではなく、テスト設計やリファクタリングの質を上げる基礎教養として学ぶ。

## 3. パーソナル AI への関心

### 現在の取り組みからの延長線

すでに「AI を自分の延長として使う」実践を積み重ねている:

- **YouTube 自動運用システム**: 21個の Claude Code スキルで企画→制作→投稿→分析の全ワークフローを AI で自動化。「自分の意思決定を AI に委譲する」経験を日常的に行っている
- **Claude Code のカスタマイズ**: 個人で作成したカスタムスキル（YouTube 用 21 + dotfiles 用 12 + 業務用数個）、CLAUDE.md によるルール定義、メモリシステムを整備。「自分の開発スタイルを AI に学習させる」仕組みを構築済み。個人で作成したスキルを業務にも活用している
- **dotfiles による環境の宣言的管理**: 開発環境全体をコード化し、AI が操作可能な状態にしている

### 目指す姿

これらの延長線上に「パーソナル AI」がある:

- **開発パートナー**: 自分のコードスタイルや設計思想を理解し、一緒に開発してくれる AI（現在の Claude Code カスタマイズの発展形）
- **知識・記憶の外部脳**: 経験・学び・判断基準を蓄積し、意思決定を支援してくれる（現在のメモリシステムの発展形）
- **業務・生活の自動化**: YouTube システムのようなワークフロー自動化を、仕事に限らず生活全般に広げる

### 現実との距離

自分で作りたい気持ちと、そういうプロダクトに関わりたい気持ちの両方がある。現時点では理想論に近く、具体的な実装プランがあるわけではない。ただし日々の AI 活用を通じて「何が自動化でき、何に人間の判断が必要か」の境界線を探り続けている。転職先として AI プロダクト企業も選択肢の一つとして考えている。

## 4. 技術的に深めたい領域

### アーキテクチャ設計

- **状態管理・データフロー**: Server/Client Component 間のデータ分割、フォームの複雑な状態設計、グローバル状態戦略
- **API 設計・データモデリング**: FE に閉じず、BE との接点（API 設計、型安全なインターフェース）も含めた設計力を伸ばしたい

### テスト設計・リファクタリング

「AI 時代のコード品質」の軸（セクション2）を支える柱として、テスト設計とリファクタリングの両方をエンジニアリングスキルとして深めたい。テスト戦略の立案（何をどのレベルでテストするか）、テスタビリティを意識したコンポーネント設計、E2E / インテグレーション / ユニットの使い分け、そしてレガシーコードの段階的改善手法など、品質を設計段階から組み込み・継続的に改善する力を伸ばしたい。高い技術基準の組織でテスト文化とリファクタリングの実践を体験することが最短ルートと考えている。

**学習ロードマップ:**

- 『単体テストの考え方/使い方』（Vladimir Khorikov）でテストの「良し悪し」の判断基準を入れる
- Testing Trophy（Kent C. Dodds）を理解し、FE のテスト戦略として specv や PJ3 に適用する
- 『テスト駆動開発』（Kent Beck）で TDD の原典と自分の実践を照らし合わせる
- テストしにくいコード = 設計の問題、という視点で既存コードのリファクタリングを実践する

### CS の基礎

情報学部等を出たわけではないため、CS の基礎を体系的に学びたい。特にネットワークの理解の浅さや、技術選定時に「なぜこの技術が良いのか」を深いレベルで説明できない場面で CS の不足を痛感している。全領域を網羅するのではなく、実務との接点がある領域から優先的に攻める。

**優先度A（実務に直結）:**

- **ネットワーク（HTTP/DNS/TCP）**: API 通信、キャッシュ戦略、CDN、SSR/SSG の判断に直結。『Real World HTTP 第3版』（渋川よしき）+ Chrome DevTools Network タブでの実践
- **データ構造の基礎**: 配列、Map、Set、木構造、計算量（O記法）。ツリービュー設計やファイルツリー（specv）で既に触れている。「なぜこの構造を選んだか」を言語化する練習

**優先度B（設計の質を上げる）:**

- **ブラウザの仕組み**: レンダリングパイプライン、イベントループ、メモリ管理。web.dev の記事群で学習。パフォーマンス改善と React の挙動理解に直結
- **認証・セキュリティの基礎**: OAuth、JWT、CORS、CSRF。PJ3 で構築した認証フローを「なぜこの方式か」で説明できるようにする

**優先度C（長期 / 面接対策）:**

- **アルゴリズム**: 『問題解決力を鍛える！アルゴリズムとデータ構造』（大槻兼資）or NeetCode 150。ブランド企業の選考を受けるなら対策が必要
- **OS / プロセス / メモリ**: Node.js ランタイムやビルドツールの挙動理解に効く。必要になったときに掘る

**学習ペース（テスト学習と並行）:**

```
Month 1:  『単体テストの考え方/使い方』+ ネットワーク基礎
Month 2:  Testing Trophy 実践 + データ構造・計算量の基礎
Month 3:  ブラウザの仕組み + 認証セキュリティの言語化
Month 4〜: アルゴリズム（面接対策が必要なら）
```

ポイントは本を読んだら必ず自分のプロジェクトに当てはめること。「PJ3 のこの部分は O(n) になっている」と紐づけることで定着する。

## 5. 情報発信

### なぜ発信するか

- **アウトプット駆動の学習**: 書くことで理解を深め、学びを定着させる
- **認知・ブランディング**: エンジニアとしての認知度を高め、キャリアの選択肢を広げる
- **コミュニティへの貢献**: 独学から転職した経験や AI 駆動開発の知見を共有し、同じ道を歩む人の役に立ちたい
- **つながり・交流**: 同じ興味を持つエンジニアとの接点を作りたい

### 現状

まだ本格的な情報発信は始めていない。specv の npm 公開が発信の一形態ではあるが、ブログや SNS での発信はこれから。

### 発信チャネル

- **個人ブログ**: 体系的な技術記事、学びの振り返り、プロジェクトの開発記録
- **X（Twitter）**: 日常的な学び・気づきの共有、コミュニティとの交流

### 発信したいテーマ

- **AI 駆動開発の実践知**: Claude Code のカスタマイズ、AI 向け設計パターン、TDD × AI の運用ノウハウなど、実務で得た知見
- **FE 設計・技術**: コンポジションパターン、状態管理戦略、モノレポ構成など、プロジェクトで試行錯誤した設計の記録
- **個人プロジェクト**: YouTube 自動運用システム、specv、dotfiles の開発過程や設計判断
- **キャリア・学習法**: 異業種からの転職経験、独学での学習プロセス、成長の振り返り
