# 自己PR

## 一言で

鳶職から完全独学でエンジニアに転職し、約1年半で BtoB 業務アプリの FE 基盤を設計・構築できるようになったフロントエンドエンジニアです。個人の実装力だけでなく、DX 改善・AI ツールの社内展開など、**チーム全体の生産性を底上げすること**に最もやりがいを感じています。

---

## 1. 失敗を設計に変える力

エンジニア歴が短い分、失敗も多く経験しています。ただ、同じ失敗は繰り返しません。

| 失敗                                       | 学び                                             | 次のプロジェクトでの改善             |
| ------------------------------------------ | ------------------------------------------------ | ------------------------------------ |
| Props が肥大化して拡張困難に               | 「何を表示するか」は利用側に委ねる               | コンポジションパターンを標準採用     |
| 共通化を省略 → 仕様変更で全箇所修正        | 共通化は「変更に強くする」ためにやる             | 仕様変更を前提にした設計を徹底       |
| 一覧画面で N+1 フェッチ                    | データ取得戦略はコンポーネント設計の段階で決める | バッチ取得・プリフェッチを前提に設計 |
| Context ベースのモーダルで SC の利点を消失 | フレームワークの進化に合わせて設計を更新する     | queryParams による状態管理に切り替え |

3つのプロジェクトを並行して担当する中で、前のプロジェクトの失敗を次のプロジェクトの設計に即座に反映してきました。3つ目のプロジェクト（ゼロベース新規構築）では、過去2つの失敗と学びをすべて設計に反映し、自身にとって最大の成功体験となりました。経験年数の短さを、改善サイクルの速さで補っています。

---

## 2. チームの中で FE 領域を自走する実行力

3〜4名の少人数チーム（PM + FE + BE）の中で、FE の設計・実装を一貫して担当してきました。

- **ゼロベースの FE 基盤構築**: ディレクトリ設計、共通コンポーネント、CI/CD、Linter/Formatter、認証・認可、テスト基盤を構築（PJ3: PM + FE（自分）+ BE 1名の体制）
- **大規模フォーム**: 52フィールド、タブ間の双方向状態同期、複雑なバリデーションを設計・実装（PJ1: PM + FE（自分）+ BE 1名）
- **モノレポ化の提案・推進**: UI不統一と保守コストの課題を自ら発見し、モノレポ構成への移行を複数回にわたって提案。個別販売時の切り出し方針など懸念にも対案を示し、AI駆動開発への最適化のタイミングと合流する形で実現（PJ2）
- **大規模マイグレーション**: Next.js 14→15 / React 18→19 / Chakra UI v2→v3 の同時アップグレードを AI を活用して約1ヶ月で完了（PJ2）
- **100件超のフィードバック対応**: 品質が不安定だった2アプリのフィードバックを2ヶ月で安定化（PJ2）

少人数チームだからこそ、BE エンジニアとの連携（API 仕様の事前すり合わせ、モックデータによる FE 先行開発）を重視し、チーム全体の開発効率を意識しています。

## 3. チームの生産性を底上げする DX 改善

自分の作業効率だけでなく、チーム全体の開発体験を改善することに最も注力しています。

**PR テンプレートの整備**

- PR テンプレートを Claude Code スキルとして整備し、レビュープロセスを効率化

**Linter / Formatter の段階的進化**

- ESLint flat config 対応 → Biome → ultracite と、プロジェクトごとに最適なツールを選定・導入
- チーム全員がコードスタイルを意識せずに書ける環境を整備

**CI/CD・品質基盤**

- GitHub Actions による PR チェック（build / lint / test）
- lefthook による pre-commit 整備

**AI × TDD による仕様駆動開発ワークフロー**

- 2025年6月に Claude Code のチーム導入を提案（個人で検証した上で提案）。経営陣の反応は「やらないとね」程度で、すぐには動かなかった
- 2025年8月、経営陣が Cursor 導入を決断（Claude Code は CLI への馴染みの薄さからか却下）。自分は Cursor 環境でも個人で Claude Code を使用し続けていた
- 後日、顧客先から AI 駆動開発の研修参加を提案され社員全員で受講。研修先が推奨していたのが Claude Code だったことで上層部が承認し、2025年11月に本格稼働
- 最初の提案が却下されても腐らず使い続けていたからこそ、導入決定後すぐに社内用のカスタムスキル整備やワークフロー構築を推進できた
- TDD と AI 駆動開発を組み合わせた開発フローを確立: 仕様を CLAUDE.md やルールで定義 → テストで期待する振る舞いを明文化 → AI が実装 → テストで品質を担保。受託開発（仕様が確定して降りてくる）との親和性が高く、仕様駆動で品質とスピードを両立

## 4. 業務外での技術への取り組み

業務時間外でも、技術的な探求と実装を継続しています。

### YouTube チャンネル自動運用システム（Python）

FE が専門だが、バックエンド（Python）でもプロダクトを作れる証拠として位置づけている個人プロジェクト。AI API（SunoAI / Gemini / Veo）と YouTube API を組み合わせ、企画→楽曲生成→動画制作→投稿→分析の全工程を自動化。現在2チャンネル運用中。

- 8ステップの自動化パイプラインを設計・実装
- Claude Code のカスタムスキル21個で全ワークフローを操作
- テンプレートリポジトリを整備し、新チャンネルの横展開を容易に

### specv — Markdown プレビュー CLI（TypeScript）

ローカルの Markdown を GitHub スタイルで表示する CLI ツールを開発し、npm に公開（v0.2.0）。React 19 + Hono + Vite で構築。Playwright E2E テスト、npm Trusted Publishing による自動配布まで整備。

### dotfiles — Nix ベース環境管理

macOS の開発環境全体を nix-darwin + Home Manager で宣言的に管理。CLI ツール、GUI アプリ、macOS 設定、Claude Code のスキル・設定まで、すべてを Git 管理下に置いている。

### リベ大フェス2025（幕張メッセ）— 子供向けプログラミング教室

親子向けプログラミング × おもちゃ作りワークショップにメインメンバーとして出店。LP サイトの開発、ワークショップでの講師、物販運営（黒字化）を担当。

## まとめ

- **チーム全体の生産性を上げる** — DX 改善、AI ツールの社内展開を通じて、自分だけでなくチーム全体の開発体験を底上げする
- **経験年数は短いが、改善サイクルが速い** — 失敗→学び→次のプロジェクトへの反映を高速で回す
- **少人数チームの中で FE を自走できる** — 設計、実装、基盤整備、品質管理まで、BE と連携しながら FE 領域を一貫して担当
- **業務外でも手を動かし続けている** — AI × 自動化の個人プロジェクトで、FE に閉じない技術の幅を広げている

### 課題認識と克服に向けたアクション

自身の課題も認識しており、それぞれに対して具体的なアクションを取っている:

- **設計の引き出し**: 経験年数の短さから設計パターンの引き出しがまだ少ない → シニアエンジニアからのフィードバックを得られる環境を求めている（転職理由の一つ）
- **BE 知識の深さ**: FE 専門のため BE の深い知識が不足 → 個人プロジェクト（Python）で補完しつつ、API 設計の理解を深めている
- **大規模チーム・育成経験**: 少人数チームでの経験が中心で、メンバー育成の実績はまだない → テンプレート・ルール・スキルなど「仕組みで底上げする」アプローチは実践済み。レビューやペアプロを通じた育成を次の環境で経験したい

鳶職時代に培った「段取り力」と「粘り強さ」は、ゼロからの FE 基盤構築や、100件超のフィードバック対応を地道にやり切る場面で活きています。現場仕事で身につけた「全体を見て工程を組む」習慣は、プロジェクトの設計判断にも通じるものがあると感じています。
